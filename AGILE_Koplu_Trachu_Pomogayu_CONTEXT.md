## 3.3. Сформулировать OKR проекта

Нужно командой:
- сформулировать OKR на основе Impact Map;
- использовать для этого слайд в итоговой презентации команды;
- приложить в LMS **скриншот слайда с OKR**.

Рекомендуемая структура:
- 1 Objective;
- 2–3 Key Results;
- KR должны быть измеримыми;
- KR должны описывать **результат**, а не активность.

Плохо:
- «сделать приложение»;
- «провести 10 интервью»;
- «разработать AR».

Хорошо:
- «не менее X из Y тестовых семей могут пройти ключевой сценарий без помощи»;
- «не менее X% родителей считают, что продукт помогает поддерживать регулярность».

## 3.4. Индивидуально пройти тест в LMS

Каждый участник команды должен самостоятельно пройти тест по курсу.

**Это блокер.**

# 4. Критерии оценивания

## Impact Map — 0–4 балла

Чтобы получить 4/4:
- карта цельная и конкретная;
- акторы релевантны цели;
- изменения поведения наблюдаемы или измеримы;
- идеи привязаны к конкретным изменениям поведения;
- нет лишних элементов;
- причинно-следственная логика читается;
- приложен читаемый скриншот в LMS.

Если скриншота нет — 0 баллов за этот пункт.

## OKR — 0–4 балла

Чтобы получить 4/4:
- есть 1 сильный Objective;
- есть 2–3 Key Results;
- KR измеримы;
- KR логично вытекают из Impact Map;
- KR отражают изменение/ценность, а не «делание»;
- приложен читаемый скриншот слайда с OKR в LMS.

Если скриншота нет — 0 баллов за этот пункт.

## Тест — 0–2 балла

- 0 — тест не пройден / нет подтверждения;
- 2 — тест пройден.

**Итого: 10 баллов.**

# 7. Суть проекта

В основе — физическая **«Умная копилка»** с тремя секциями:

1. **Коплю**
2. **Трачу**
3. **Помогаю**

Ребёнок получает карманные деньги и сам распределяет их между тремя секциями.

Это помогает:
- познакомиться с ценностью денег;
- учиться планированию;
- формировать финансовые привычки;
- понимать различие между накоплением, тратами и помощью другим.

# 8. Главная проблема

На первом контакте всё работает достаточно хорошо:
- ребёнок знакомится с копилкой;
- семья получает материалы;
- есть мастер-классы и активности;
- ребёнок начинает пользоваться копилкой.

Потом возникает разрыв:

**семья получила копилку → некоторое время использует → НЦФГ теряет контакт**

НЦФГ практически не видит:
- продолжает ли ребёнок пользоваться копилкой;
- как часто;
- есть ли прогресс;
- обсуждают ли родители с ребёнком деньги;
- какие трудности возникают;
- насколько методика эффективна в долгую.

Дополнительная проблема: материалы разрознены.

Есть:
- физическая копилка;
- сказки;
- трекеры;
- материалы;
- сайт;
- соцсети;
- мастер-классы.

Но нет единой цифровой среды, связывающей семью и НЦФГ после первого контакта.

# 9. Главная продуктовая задача

Создать концепцию цифрового продолжения физической «Умной копилки», которое объединит:
- ребёнка;
- родителя;
- физическую копилку;
- материалы проекта;
- НЦФГ.

Рабочая формулировка:

> Создать цифровую среду вокруг физической копилки, которая поможет ребёнку 6–10 лет регулярно пользоваться методикой «Коплю–Трачу–Помогаю», родителю — поддерживать ребёнка и видеть прогресс, а НЦФГ — получать обратную связь и понимать эффективность методики.

# 10. Целевые аудитории

## 10.1. Дети 6–10 лет

Важно:
- не превращать продукт в ещё один школьный урок;
- делать взаимодействие простым и игровым;
- давать понятную практику;
- показывать прогресс;
- поддерживать мотивацию;
- связывать цифровые действия с реальной физической копилкой.

Потенциальные механики:
- прогресс;
- награды;
- уровни;
- игровые задания;
- визуализация финансовой цели;
- AR;
- достижения;
- регулярные небольшие действия.

## 10.2. Родители

Для родителей нужен простой инструмент, который:
- показывает прогресс ребёнка;
- помогает поддерживать регулярность;
- даёт подсказки;
- даёт задания/темы для обсуждения;
- содержит полезные материалы;
- позволяет задать вопрос;
- позволяет оставить обратную связь.

Важно: не каждый родитель сам хорошо разбирается в финансовой грамотности.

## 10.3. НЦФГ

НЦФГ нужно:
- не терять контакт с семьёй;
- видеть, используется ли методика дальше;
- получать обратную связь;
- понимать эффективность инструментов;
- иметь данные о регулярности;
- понимать проблемные места и потребности родителей/детей.

# 11. Желаемый продукт по видению заказчика

## 11.1. Цифровой трекер копилки
Пользователь может видеть:
- три секции;
- накопления;
- движение к цели;
- историю.

## 11.2. Родительская часть
Родитель может:
- видеть прогресс ребёнка;
- получать подсказки;
- получать задания;
- получать материалы;
- давать НЦФГ обратную связь.

## 11.3. Механики регулярности
Примеры из презентации:
- «Задания недели»;
- напоминания;
- «День привычек».

## 11.4. AR-игра
Важно: AR обозначена как дополнительная механика, **если позволяют ресурсы и навыки команды**.

Идея:
1. на физической копилке есть QR-код;
2. ребёнок сканирует QR;
3. открывается игра;
4. камера смартфона показывает копилку;
5. сверху падают виртуальные монетки;
6. монетки относятся к категориям Коплю / Трачу / Помогаю;
7. ребёнок распределяет/собирает нужные монетки;
8. игра связывает цифровой и физический опыт.

## 11.5. Возможный AI-помощник для родителей
Из устного брифа:
- родитель задаёт вопросы;
- получает рекомендации;
- желательно опираться на методологию НЦФГ;
- это должно быть удобнее, чем писать на почту.

Это пока идея и требует валидации.

# 15. Возможный OKR — база

## Objective
**Сделать цифровое продолжение «Умной копилки» полезным и понятным для семьи, чтобы ребёнку было проще регулярно практиковать финансовые привычки, а родителю — поддерживать этот процесс.**

Важно: финальные KR нельзя честно фиксировать без понимания:
- размера тестовой выборки;
- текущей регулярности;
- периода измерения;
- доступа к реальным семьям.

Примеры формата KR:
- **KR1:** не менее `X из Y` протестированных семей могут самостоятельно выполнить ключевой сценарий цифровой копилки без помощи команды.
- **KR2:** не менее `X%` родителей после теста подтверждают, что продукт помогает им понимать прогресс ребёнка и поддерживать регулярную практику.
- **KR3:** не менее `X%` детей из тестовой выборки готовы повторно вернуться к механике/заданию после первого использования.

Если нет доступа к реальным пользователям — согласовать допустимые proxy-KR.

# 20. Чек-лист перед отправкой в LMS

- [ ] Команда записана в таблицу.
- [ ] Представитель НКО знаком с командой.
- [ ] Impact Map сделана.
- [ ] На карте есть Goal.
- [ ] Есть релевантные Actors.
- [ ] Для каждого актора есть наблюдаемые Impacts.
- [ ] Ideas/Deliverables привязаны к Impacts.
- [ ] Нет лишних фич без связи с целью.
- [ ] Сделан читаемый скриншот Impact Map.
- [ ] Есть 1 Objective.
- [ ] Есть 2–3 измеримых KR.
- [ ] KR описывают результат, а не действия.
- [ ] OKR логично вытекает из Impact Map.
- [ ] Сделан читаемый скриншот OKR-слайда.
- [ ] Оба скриншота загружены в LMS.
- [ ] Каждый участник команды прошёл тест в LMS.

# 21. Критическая оговорка по метрикам

Нельзя придумывать фактические показатели, которых заказчик не давал.

Например, нельзя утверждать:

> «Сейчас retention = 10%, поднимем до 40%»

если такого baseline никто не сообщал.

Если конкретной базы нет:
- используйте метрику пилотного теста;
- обозначайте X/Y как значения, которые команда согласует;
- или согласуйте proxy-метрики с преподавателем.

Это лучше, чем выдумывать цифры.
